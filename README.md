# Prompt Engineering для LLM/Gen AI — лабораторні (IntelliJ IDEA, Gemini і Claude)

Репозиторій курсу «Prompt Engineering для LLM/Gen AI». Тут код усіх лабораторних: ви **один раз клонуєте** репозиторій, а кожну
нову лабу отримуєте через **Git → Pull**. У Google Classroom до кожної лаби — лише документи (інструкція, пакет вхідних даних,
шаблон звіту, рубрика) і посилання сюди. Усі лаби виконуються **кодом** в IDEA; браузер потрібен лише один раз — створити API-ключ.

Адреса репозиторію: **https://github.com/eugeneol/promptengineering-lab**

## 1. Як отримати проєкт (перший раз)

Потрібні IntelliJ IDEA (Community підійде) і JDK 17+ (рекомендовано 21; IDEA вміє завантажити:
`File → Project Structure → SDK → Add SDK → Download JDK`).

**Спосіб А — з IntelliJ (рекомендовано).** `File → New → Project from Version Control…` → у поле **URL** вставте адресу
репозиторію → виберіть папку (наприклад, `prompt-lab`) → **Clone** → **Trust Project**. Якщо IDEA попросить встановити Git —
погодьтесь. Коли проєкт відкриється, дочекайтесь імпорту Maven (праворуч вікно **Maven** → ⟳ **Reload All Maven Projects**,
якщо класи червоні). Конфігурації запуску «Лаба N · …» з'являться у списку поруч із кнопкою ▶.

**Спосіб Б — командний рядок:**

```
git clone https://github.com/eugeneol/promptengineering-lab.git
```

потім у IDEA `File → Open…` → `pom.xml` → **Open as Project**.

**Спосіб В — без git:** на сторінці репозиторію **Code → Download ZIP**, розпакуйте й відкрийте `pom.xml` як проєкт.
Нові лаби так не підтягнуться: для кожної лаби доведеться завантажити ZIP заново в **нову** папку і перенести туди `.env` і свої
файли (таблиця в розділі 3). Тому краще спосіб А.

## 2. Файл .env (ключ і варіант)

1. Створіть ключ Gemini (безплатно): <https://aistudio.google.com/apikey> (Google AI Studio → **Get API key** → Create API key).
2. У корені проєкту скопіюйте `.env.example` у `.env`: у вікні Project клацніть `.env.example` → Ctrl+C → клацніть кореневу
   папку → Ctrl+V → ім'я `.env` (macOS — ⌘C / ⌘V). Копіюйте саме в IDEA: у Провіднику / Finder файли з крапкою приховані.
3. Впишіть ключ одразу після `GEMINI_API_KEY=` (без лапок і пробілів). Для Claude — `LAB_PROVIDER=claude` і `ANTHROPIC_API_KEY=…`
   (для лаби 4 ключ Gemini потрібен усім — ним рахуються ембединги).
4. Допишіть свій варіант: `LAB_VARIANT=N`, де N = ((номер у журналі − 1) mod 8) + 1. Рядок `LAB_DELAY_MS=4000` уже є — не видаляйте.

`.env` створюється один раз і служить усім лабам. Він у `.gitignore`: у git не потрапляє, і Pull його не чіпає.
Ключ — як пароль: не у звіт, не на скріншоти, не в Run → Edit Configurations → Environment variables (конфігурації лежать у репозиторії).

## 3. Як підтягнути нову лабу

**Git → Pull** (Ctrl+T, macOS ⌘T) → OK. З'являться новий пакет і нові конфігурації запуску; якщо класи червоні — вікно Maven →
⟳ Reload All Maven Projects.

**Головне правило: редагуйте лише файли з таблиці нижче і `.env`** — тоді Pull пройде без конфліктів. Викладач ці файли після
публікації лаби не змінює. Не змінюйте інші класи, JSON варіантів і конфігурації запуску (налаштування — у `.env`).

| Лаба | Файли, які ви редагуєте за інструкцією (шлях від `src/main/java/ua/knu/promptlab/`) |
|---|---|
| 1 | лише `.env`; за бажанням — `steps/Step6PromptVariants.java` (крок 6: свій варіант D, додаткове правило в `checkFormat`) |
| 2 | `lab2/TicketValidator.java` (метод `validate()` — ваші правила), `src/test/java/ua/knu/promptlab/Lab2Test.java` (тести до них), `lab2/MySchema.java` (домашня схема) |
| 3 | `lab3/MyPromptTweaks.java` |
| 4 | `lab4/MyQuestions.java`, `lab4/MyRetrievalTweak.java` |

`Step6PromptVariants`, `TicketValidator` і `Lab2Test` — спільні класи, але викладач їх після публікації лаб 1–2 не змінює, тож Pull
їх не зачепить. Опційний дослід кроку 6 лаби 2 (зміна системного промпта в `TicketData.SYSTEM` або в `lab2/variants/V0N.json`)
після досліду поверніть назад: правий клік на файлі → **Git → Rollback…**

**Якщо Pull каже про конфлікт** («Your local changes would be overwritten…» або файл позначено червоним):

- ви випадково змінили чужий файл і правки не потрібні → правий клік на файлі → **Git → Rollback…** (повертає файл як у
  репозиторії), потім Pull ще раз;
- правки потрібні → **Git → Uncommitted Changes → Stash Changes…** (сховати), Pull, потім **Git → Uncommitted Changes →
  Unstash Changes…** (повернути); якщо IDEA покаже конфлікт — для чужих файлів виберіть «Accept Theirs», для своїх — «Accept Yours»;
- якщо заплутались — склонуйте репозиторій у нову папку і перенесіть туди `.env` і свої файли з таблиці вище.

## Режим MOCK (без ключа)

Конфігурації з «MOCK» у назві (або змінна `LAB_MOCK=1`) піднімають локальну імітацію API. **Відповіді шаблонні, а кількість токенів —
груба евристика, а не справжній токенізатор.** Для лабораторної потрібен справжній ключ; у консолі в цьому режимі завжди є рядок `РЕЖИМ MOCK`.

## Варіанти (лабораторні 1–3)

У `.env` задайте `LAB_VARIANT=N`, де N = ((номер у журналі − 1) mod 8) + 1 — один номер на всі три лабораторні.

- **Лабораторна 1** (`steps/Lab1Variant`, дані — `src/main/resources/lab1/variants/V01.json … V08.json`): місто (кроки 1–3 і 6),
  абзац UA/EN у кроці 4 (інша тема, та сама довжина ±10 %), що називаємо в кроці 5 і вимоги формату кроку 6,
  які перевіряє `Step6PromptVariants.checkFormat(text, format)` (3–5 пунктів, 10–15 слів; у варіантах 5–8 — ще одна вимога).
- **Лабораторна 2** (`lab2/Lab2Variant`, дані — `src/main/resources/lab2/variants/V0N.json`): домен тікетів і продукт у системному
  промпті, 10 повідомлень з очікуваними category / priority і обов'язкове правило для `TicketValidator.validate()`. Схема, категорії,
  p0–p3 і sentiment — спільні.
- **Сумісність:** без `LAB_VARIANT` лабораторні 1–2 беруть варіант 1 — побайтово ті самі дані, що були до появи варіантів
  (`TicketData` для лаби 2) — і друкують одне речення-нагадування. Лабораторна 3 без `LAB_VARIANT` на справжній моделі не запускається.
- Імітація (MOCK) знає всі варіанти; тести — `Lab1VariantsTest`, `Lab2VariantsTest`. Не змінюйте JSON варіантів: інакше ваші числа
  не порівняти з однокурсниками того самого варіанта.

## Структура коду

- `LlmClient` — спільний інтерфейс; `ClaudeClient` та `GeminiClient` — реалізації (REST без SDK).
  Саме цей інтерфейс студенти розширюватимуть у наступних лабах (шаблони промптів → структурований вивід → tool calling → агент).
- `HttpJson` — POST із JSON і повторами при 429 / 5xx (з паузою за `Retry-After`, якщо сервер її надіслав).
- `Pricing` — ціни за 1 млн токенів. Джерела вказано в коментарі; **ціни змінюються — звіряйте перед заняттям**.
  Для Gemini це еквівалент платного тарифу: на безкоштовному рівні реальна вартість $0.
- `Config` — `.env` + змінні середовища; ключ у коді не зберігається.
- `mock/FakeLlmServer` — імітація обох API для тестів і демо без ключа.

## Відмінності Gemini від Claude, які варто показати

- Ліміт вихідних токенів у Claude (`max_tokens`) обов'язковий, у Gemini (`maxOutputTokens`) — ні.
- System prompt: `system` у Claude, `systemInstruction` у Gemini; повідомлення: `messages[]` проти `contents[].parts[]`.
- Ключ: заголовок `x-api-key` проти `x-goog-api-key`.
- Gemini «міркує» перед відповіддю: ці токени (`thoughtsTokenCount`) входять у вихідні й у ліміт, тому при малому
  ліміті текст може бути коротким або порожнім (крок 2б). Рівень міркування можна задати через `LAB_THINKING_LEVEL`
  (експериментально, за замовчуванням не надсилається).
- `temperature` необов'язкова в обох клієнтах: якщо модель відповідає 400 про temperature (так роблять новіші моделі,
  наприклад Claude Sonnet 5.5), клієнт один раз пише про це в консоль і до кінця прогону надсилає запити без неї
  (`LlmClient.temperatureSupported()`). Для Gemini 3 Google радить лишати temperature 1.0 (значення за замовчуванням).
- Безкоштовний рівень Gemini має ліміти запитів на хвилину (≈15). У `.env.example` уже стоїть `LAB_DELAY_MS=4000` —
  пауза між запитами в циклах (крок 5 і Step7). Якщо все одно бачите 429 — збільште паузу.

## Лабораторна 2. Структурований вивід і валідація

Новий пакет `ua.knu.promptlab.lab2`:

| Клас | Що робить |
|---|---|
| `Ticket` | record тікета підтримки: category, priority, sentiment, summary, steps |
| `TicketSchema` | JSON Schema для запиту (Gemini `responseJsonSchema`, Claude `output_config`) і її словесна версія для промпта |
| `TicketValidator` | ворота валідації: форма (строгий Jackson: текст після JSON і відсутнє поле — помилка) → карти нормалізації міток → правила змісту; повертає одне речення-причину |
| `JsonGate` | виклик → перевірка → повтор з причиною, не більше `maxRetries` |
| `TicketData` | 10 повідомлень клієнтів з очікуваною категорією і пріоритетом — перший eval-набір (варіант 1) |
| `Lab2Variant` | дані варіанта з `LAB_VARIANT`: домен, системний промпт, 10 повідомлень, обов'язкове правило (варіант 1 = `TicketData`) |
| `Step7StructuredOutput` | кроки 7.1–7.6 лабораторної |
| `MySchema` | **ваш файл** для домашньої схеми з лекції 3: задача, системний промпт, JSON Schema, три входи, правила `validate(JsonNode)` |
| `MySchemaRun` | перевірка вашої схеми на трьох входах (конфігурації `Лаба 2 · 8 My schema` і `(MOCK)`; 3 запити) |

У `LlmClient` додано `askJson(system, user, jsonSchema, maxTokens)` і `buildJsonRequest(...)`; реалізації — у `GeminiClient`
(з переходом на старіше поле `responseSchema`, якщо API відповість 400 про `responseJsonSchema` / «Unknown name» /
«Invalid JSON payload»; яке поле використано — друкується) і `ClaudeClient` (перед відправкою `toClaudeSchema` прибирає ключі,
на які Claude відповідає 400: `maxItems`, `minItems` > 1, `minimum`/`maximum`, `minLength`/`maxLength`; ці правила перевіряє `validate()`).

Імітація (`LAB_MOCK=1`): без схеми (7.1) — обгортки, текст після JSON, «critical» замість p0, 7 кроків; зі схемою — форма завжди
за схемою, але частина відповідей має неправильний ЗМІСТ (побажання з p0, задовгий summary), і один кейс не виправляється
жодним повтором. Числа з імітації (p = 0.70, v = 2/3, p_eff = 0.90) — лише для перевірки, що все працює.

Конфігурації запуску: `Лаба 2 · 7 Structured output` і `Лаба 2 · 7 Structured output (MOCK)`; домашня схема — `Лаба 2 · 8 My schema`
і `Лаба 2 · 8 My schema (MOCK)` (імітація відповідає найпростішим JSON за вашою схемою). Тести: `Lab2Test`, `Lab2MySchemaTest`.
Запитів до API за прогін ≈ 25 (Step7 завжди проганяє всі шість кроків); тримайте `LAB_DELAY_MS=4000`.

## Лабораторна 3. Від одного вдалого прикладу до виміряної точності

Питання лаби: які прийоми справді підвищують точність і чи більший їхній ефект за шум однакових прогонів. Задача — бот підтримки
студентів факультету: класифікувати звернення студента за трьома мітками (`category` — study / electives / schedule / scholarship /
dorm / access / other; `urgency` — low / normal / high; `needs_human` — true / false). Правильна відповідь — коли збіглися всі три
мітки; для кількох спірних звернень допустимі дві відповіді (поле `alt` у JSON, у консолі — через «|», наприклад `normal|low`).

**Як отримати.** Перший раз — склонуйте репозиторій (розділ 1), якщо вже маєте — **Git → Pull** (розділ 3). Ваша правка — лише
в `MyPromptTweaks.java`. Якщо IDEA не бачить нових класів — вікно Maven (праворуч) → кнопка ⟳ Reload All Maven Projects.

**Варіанти.** У `.env` задайте `LAB_VARIANT=N`, де N = ((номер у журналі − 1) mod 8) + 1. Дані варіантів —
`src/main/resources/lab3/variants/V01.json … V08.json`: 15 звернень з очікуваними мітками (5 — пастки: сарказм, дві теми, суржик,
«терміново» без суті тощо; набір пасток у кожного варіанта свій), 3 приклади few-shot (не схожі на тестові звернення — перевіряє тест)

Наприкінці — дві підсумкові таблиці («на всіх 15» і «на 5 найважчих»: база / +reasoning / effort low / effort high / голосування,

зберігаються в `target/lab3-results.md` (цей файл, `target/lab3-cache.json` і лог консолі додають до звіту). Файл самопояснювальний:
легенда позначень на початку, перед кожною таблицею — що це і на яке питання відповідає, після — як читати кожну колонку і приклад.

**temperature у лабі 3 не надсилається** (значення моделі за замовчуванням): новіші моделі її відхиляють, а для Gemini 3 Google
радить лишати 1.0. Шум і голосування — з налаштуванням за замовчуванням.

**Правило для висновків.** Ефект техніки = її точність − база. Якщо |ефект| не більший за розкид двох однакових прогонів
(не менше 1 звернення), висновку немає. На 15 зверненнях одне звернення = 6,7 п.п., на 5 — 20 п.п.

**Кеш відповідей** — `target/lab3-cache.json`: ключ = SHA-256 від провайдера, моделі, режиму (MOCK чи ні), мітки вибірки (s1/s2/s3)
і параметрів запиту (системний промпт із прикладами, текст звернення, схема, ліміт, temperature, рівень міркування effort). Повторний прогін бере все
з кешу (0 запитів); після 429 чи падіння досить запустити ще раз — прогін продовжиться. `LAB_NO_CACHE=1` вимикає диск; щоб почати
з нуля, видаліть файл. `LAB_DELAY_MS` діє лише перед новими запитами. MOCK пише в окремі файли `target/lab3-cache-mock.json`
і `target/lab3-results-mock.md`, щоб імітація не змішувалась зі справжніми відповідями.

**Рівень міркування (effort).** У `LlmClient` є `askJson(..., CallOptions)`: `CallOptions(temperature, effort, reasoningField)`,
де `Effort` — DEFAULT / MINIMAL / LOW / MEDIUM / HIGH, `reasoningField` — поле `reasoning` першим у схемі, temperature — null
(не надсилається). Клієнт сам перекладає рівень у параметр свого API, а крок 4 друкує, що саме реально надіслано:

- Gemini 3+ — `generationConfig.thinkingConfig.thinkingLevel` = `minimal` / `low` / `medium` / `high` (`minimal` — не обов'язково
  0 токенів міркування; 3.1 Pro не приймає `minimal` — тоді клієнт повторює без `thinkingConfig` і пише про це);
- Gemini 2.x (або якщо задано `LAB_THINKING_BUDGET`) — `thinkingBudget`: 0 / 1024 / 2048 / 4096 (high — або `LAB_THINKING_BUDGET`);
- Claude 5.x — `thinking: {type: "adaptive"}` + `output_config.effort` = `low` / `medium` / `high`; мінімальне — `thinking:
  {type: "between_tools"}` + effort `low` (найнижче; `disabled` і `budget_tokens` 5.5 відхиляє); `max_tokens` = ліміт + запас на міркування;
- Claude 4.x / Haiku 4.5 (effort не приймає → 400) — `thinking: {type: "enabled", budget_tokens: 1024 / 2048 / 4096}`, мінімальне —
  без thinking. Механізм визначається за ПЕРШОЮ 400-помилкою про effort і запам'ятовується до кінця прогону (`ClaudeClient.mechanism()`);
  консоль пише, який механізм реально використано.

Для effort low / high мовчазного фолбеку немає: якщо модель відхилила параметр, рядок пропускається з поясненням.
Claude не повідомляє токени міркування окремо — вони вже в `output_tokens` (у таблицях — «н/д»); блоки thinking у відповіді
клієнт пропускає, бере лише text. Для старішого поля Gemini `responseSchema` порядок полів (reasoning першим) задає
`propertyOrdering` — його додає `GeminiClient.toLegacySchema`.

## Лабораторна 4. Бот знаходить пункт положення

Питання лаби: як бот підтримки знаходить у положеннях університету потрібний пункт і відповідає з цитатами — і як це виміряти.
Кроки — як на слайді «Лабораторна 4» лекції 4. Склонуйте репозиторій або зробіть **Git → Pull**, Maven → Reload,
конфігурації `Лаба 4` і `Лаба 4 (MOCK)`. **Кожен запуск перезаписує `target/lab4-results.md` — здавайте останній прогін**
(у ньому вже є ваші питання, ваш важіль пошуку і бонус).

**Корпус — 17 положень університету.** Їхні тексти належать університету й використовуються лише для навчання, тому в проєкт вони
не входять: `CorpusLoader` сам завантажує PDF з efund.cnu.edu.ua (список id / назва / шифр / адреса — `src/main/resources/lab4/corpus.json`),
перевіряє, що це PDF («%PDF») до запису на диск, витягує текст PDFBox, прибирає колонтитули й номери сторінок (`PdfText.clean`) і кешує
текст у `target/lab4-corpus/<id>.txt`. Якщо сайт недоступний — консоль скаже, які PDF завантажити вручну в `lab4-pdf/<id>.pdf`.
`LAB4_OFFLINE=1` — не завантажувати; `LAB4_PDF_DIR` — інша папка з PDF. Після завантаження код перевіряє еталонні фрагменти свого
варіанта: якщо положення оновилось і фрагмента немає, питання виключається з метрик з поясненням.

**Ембединги.** Ключ Gemini обов'язковий для всіх: ембединги рахує лише `gemini-embedding-2` (768 чисел, `batchEmbedContents`, до 100
текстів у пакеті; вектор має бути рівно 768 чисел), навіть якщо відповіді генерує Claude. Шматки однакові для всіх варіантів, тож
їх індексує **викладач** (клас `TeacherIndex`, запуск його `main`; студентам не потрібно): він бере вектори з
`target/lab4-embeddings.tsv`, дораховує решту і пише `src/main/resources/lab4/embeddings-cache.bin.gz` (int16, gzip, лише ключі SHA-256 і
числа — тексту положень немає). Студентський прогін бере вектори з цього кешу; шматки, яких там немає (PDF оновився), рахує сам і пише
про це. Кеш у проєкті: 2844 вектори (усі шматки трьох нарізок і питання всіх варіантів), 3,8 МБ, зібрано 12.11.2026. Без кешу
індексація — ≈2,8 тис. текстів (≈520 тис. токенів, ≈30 пакетів), а безплатний тариф дає ≈1000 текстів ембедингів на добу (кожен текст
у пакеті рахується окремо): за день не встигнути, тому кеш викладача обов'язковий. Пауза між пакетами рахується за токенами
(`LAB_EMBED_TPM`: 30 000 за замовчуванням для безплатного тарифу, 300 000 — платний), на 429 код чекає `retryDelay` з тіла відповіді,
добовий ліміт — зрозуміле повідомлення «продовжіть завтра, кеш збережено». Перед кешем викладача програма дивиться у ваш
`target/lab4-embeddings.tsv`. Усі HTTP-заголовки — лише ASCII (User-Agent з кирилицею ламав завантаження PDF; тест `httpHeadersAreAscii`).
